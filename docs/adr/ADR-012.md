# ADR-012: Rig maths conventions (refines spec §3.4.7)

- **Status**: Accepted (2026-10-27, orchestrator; T3.1)
- **Date**: 2026-10-27

## Context
Spec §3.4.7 says a child's rest position is "an offset from its parent's pivot, in the parent's rotated frame", and the T3.1 card rotates that offset by the parent's quantised **world** angle. Implementing it (T3.1) showed three problems with that literal reading, where the canvas rest position is `round(R(parent rest world angle) · v)` for a stored integer `v`:

1. **Unreachable rest poses.** Rounding a rotated integer lattice is not onto. At a 45° parent rest angle, 24 of the 169 canvas offsets within ±6 px have no integer `v`, (−5, 0) among them; at 80° or 100°, (±3, ±3). An author cannot put the elbow on the pixel where it was drawn, so the rest render differs from the drawn art (W2b recomposition, overrides anchored at rest).
2. **The rest pose depends on the quantum.** The rest angle must be quantised to index the trig table, so with `angleQuantum` 45° a parent at rest 100° turns its children by 90°: `v = (0, 6)` lands at (−6, 0) instead of (−6, −1). One document would have different rest poses in different animations.
3. **Skeleton and art disagree at rest** by the rest angle's quantisation error (up to q/2): parts drawn at rest are not rotated (residual 0), but the child offsets are.

## Decision
1. **Rest positions are canvas offsets at rest.** A child's rest `(x, y)` is its pivot's canvas offset from the parent's pivot in the rest pose (the schema TSDoc's "both at rest"). A bone's frame at rest is the canvas frame; posing turns it by the bone's **rotation away from rest**: `child = parent.pivot + rotatePoint(rest.x, rest.y, parent.rotation) + offset`, where `rotation` is the sum of the quantised key angles of the bone and its ancestors. Rest angles never move pivots; they are bone directions.
2. **Angles.** Each key angle (relative to rest) is quantised on its own, half away from zero, so negation is exact (mirrored paste, FR-RIG-17). Rest angles are parent-relative, summed exactly down the chain and quantised once (`restAngle`). `worldAngle = restAngle + rotation`, equal to the card's "parent world + rest + key" whenever rest angles are multiples of the quantum.
3. **Interpolation** is by frame index (retiming never re-poses), uses the previous key's `interp`, takes ease-in-out as the smoothstep `3t² − 2t³`, holds outside the keys, and wraps from the last key to the first in `loop` animations (`once`, `pingpong` hold). It is exact BigInt rational arithmetic with one rounding.
4. **Bones without a rest entry** in a view are evaluated at rest `(0, 0, 0)` and flagged `inView: false`; not an error. Offset keys are canvas pixels added after the rotation.

## Consequences
- With no keys every pivot is its authored canvas position at any quantum and any rest angles; parts at rest render exactly as drawn. In exact arithmetic this equals the §3.4.7 model (`v_canvas = R(rest world) · v_local`); only rounding differs. Reverting is one line in `snapSkeleton` (rotate by `parent.worldAngle`) plus inverse-rotating rest offsets in T3.2.
- Half away from zero is odd-symmetric but not translation-equivariant at a tie: an interpolated offset of exactly k + ½ may shift one pixel more than a translated copy. Rest positions and keyed offsets are translation-exact.
- Oracle correction for T3.1 (e): independent per-bone rounding also satisfies the card bound `ceil(L·Δθ) + 1` (per axis it moves the joint by < |Δv| + 2). The tests detect it with the tight bound `ceil(L·Δθ)` and "Δθ = 0 ⇒ the parent→child vector is unchanged", which hierarchical snapping meets on all 11 188 random frame pairs.
- T3.3: a variant without `drawnAngle` rotates by `rotation`; one with a `drawnAngle` by `worldAngle − drawnAngle`, quantised.
