# @pixel-forge/rig

FK/IK, key interpolation and quantisation, snapping, variant selection, part render, overrides and staleness, joint check, presets and templates.

**Depends on:** `schema`, `raster`

**Status:** T3.1: forward kinematics, key interpolation and quantisation, hierarchical snapping (FR-RIG-10/11/12, FR-RIG-20 steps 1–2). T3.2: templates, part names, overlap binding. T3.3: the part render pipeline, part overrides and staleness (FR-RIG-20 steps 3–4, FR-RIG-21/22; see "Part render and overrides"). T3.4: the joint check (FR-RIG-05; see "Joint check (T3.4)"). T3.8: edit attribution (FR-RIG-22/24; see "Edit attribution"). The pose clipboard (T3.6) comes later.

Pure: no Node built-ins, no clock, no randomness, and **no floating-point trig or accumulation** in any decision. Angles are exact BigInt rationals until they are rounded once; rotations use raster's committed Q16 table (NFR-02, ADR-010). The conventions are recorded in [ADR-012](../../docs/adr/ADR-012.md) (Accepted), which refines spec §3.4.7.

Inputs are structural and read-only: a schema `Rig`, `View` and `AuthoredAnimation`, or the `DeepReadonly` versions core hands to the rig hook, fit directly. A `MirrorAnimation` does not (it has no frames): evaluate its source; mirrors are flipped in core (FR-RIG-16, T3.6).

`SnappedBone`: `id`, `parentId?`, `inView`, `pivot` (integer canvas pixel), `key` (the resolved local key: `angle` relative to rest and **not** normalised, `offset`, `flipX`), and the `WorldTransform` fields, all degrees in `[0, 360)` and multiples of the quantum:

- `rotation`: rotation away from the rest pose, the sum of the quantised key angles of the bone and its ancestors. It rotates the bone's children's rest offsets, and it is the residual of a part variant drawn at rest (no `drawnAngle`).
- `restAngle`: the bone's world direction at rest (its rest angle plus its ancestors', summed exactly, quantised once).
- `worldAngle`: `restAngle + rotation`, the world direction now (variant auto-select, gizmos, IK).
- `flipX`: mirror the bone's own parts; not inherited.

## Conventions (spec §3.4.7 as refined by ADR-012)

- Angles are degrees, 0° along +x, clockwise on screen (y down). `BoneKey.angle` is relative to the rest angle. Rest angles are relative to the parent (a root's is a world angle).
- **Rest positions are canvas offsets at rest.** A root's rest `(x, y)` is its canvas pivot. A child's rest `(x, y)` is its pivot's canvas offset from the parent's pivot **in the rest pose**; it turns with the parent's rotation away from rest. Rest angles never move a pivot. So with no keys every pivot is exactly where it was authored, whatever the rest angles and the quantum, and parts render at rest exactly as drawn. (The literal §3.4.7 reading, an offset in the parent's frame rotated by its rest angle, cannot reach every canvas pixel and makes the rest pose depend on the quantum; see ADR-012.)
- Offset keys are integer canvas translations, added after the rotation. `flipX` flips only the bone's own parts.
- A missing `interp` is `linear`. An undirected animation uses `views[0]`.
- A bone with no rest entry in the view is unused there (its parts are hidden, schema `View`). It is still evaluated with rest `(0, 0, 0)` and reported with `inView: false`, so it passes its parent's pivot and rotation through to any children. This is not an error.
- `Frame.rootMotion` is engine data (FR-ANIM-08) and never moves the skeleton.

## Step 1: key resolution and interpolation (FR-RIG-11, FR-RIG-12)

Keys are sparse (`Frame.boneKeys`). Each channel (`angle`, `offset`, `flipX`) is resolved on its own, over the frames that key that channel:

- **By frame index, not by time.** `t = i / n`, where `i` counts frames from the previous key and `n` from the previous to the next key. Durations are timing and keys are spacing: a hold is a longer duration (FR-ANIM-03), and lengthening or shortening a frame must not move any pose. Time-based interpolation would re-pose every in-between whenever a frame is retimed.
- **The previous key's `interp`** decides a segment: `step` holds its value; `linear` is `t`; `ease-in-out` is the cubic smoothstep `w = 3t² − 2t³` (zero slope at both keys, symmetric `w(1 − t) = 1 − w(t)`). `flipX` always steps.
- **Before the first / after the last key** the nearest key holds (`once`, `pingpong`; a ping-pong never plays last → first). A **`loop`** animation wraps instead: after the last key the segment runs to the first key one loop later, and before the first key it runs from the last key one loop earlier, so a cycle flows across its seam. A single key holds everywhere. A channel no frame keys is at rest (angle 0, offset (0, 0), flipX false).
- **Angles are raw degrees**: no unwrapping and no shortest path. 0 → 720 spins twice; 350 → 10 goes back through 180.
- **Exact arithmetic.** Each double is converted to its exact value `m / 2^e`; `value = a + (b − a)·N/D` is a BigInt rational; it is rounded **once**, half away from zero, to a multiple of the quantum `q` (`opts.angleQuantum ?? animation.angleQuantum ?? 1`). Offsets are interpolated the same way and rounded half away from zero to integers. Example: float64 gives `0.3 + (0.7 − 0.3)/2 = 0.5`, a tie that would round to 1°; the exact midpoint of the doubles is 0.49999999999999997224, which rounds to 0°.

Every key of the animation is validated up front (`prepareAnimation`), not just the ones the frame uses, so errors never depend on the frame: each key's angle is quantised and must stay below 2^51° (quantisation is monotone, so every interpolation between valid keys is valid too), offsets must be in-range integers, `interp` known, and every keyed bone in the rig. An invalid key at frame 2 makes frames 0 and 1 throw as well.

## Step 2: hierarchical snapping (FR-RIG-20 step 2)

For every bone in `boneOrder` (parents first):

```text
a          = round(key.angle / q) · q                        local, relative to rest; half away from zero
rotation   = parent.rotation + a                             (root: a)
pivot      = root:  rest.(x, y) + key.offset
             child: parent.pivot + rotatePoint(rest.x, rest.y, parent.rotation) + key.offset
restAngle  = round((Σ rest.angle over the bone and its ancestors) / q) · q
worldAngle = restAngle + rotation                            (rotation, restAngle, worldAngle in [0, 360))
```

`rotatePoint` is raster's fixed-point rotation: `[C·dx − S·dy, S·dx + C·dy]` with the Q16 table values `C = cosQ16(θ)`, `S = sinQ16(θ)`, each coordinate rounded half away from zero. That rounding is the **only** rounding of a child pivot, and its result is added to the parent's **snapped** integer pivot. A child pivot is never rounded independently of its parent, so:

- the vector parent → child (minus the child's own offset key) is a function of the parent's rotation alone: a translation anywhere up the chain moves the whole subtree by exactly the same integers, and a constant parent rotation keeps the joint exactly still;
- between two frames that vector changes by at most `ceil(L·Δθ)` per axis (`L = |rest offset|`, `Δθ` the change of the parent's rotation in radians), up to an exact .5 tie; the card's bound `ceil(L·Δθ) + 1` holds with room to spare.

Rest angles are summed exactly and quantised once, so a chain of rest angles that are not multiples of `q` does not accumulate rounding (rest angles 0.4°, 0.4°, 0.4° give rest directions 0°, 1°, 1°, not 0°, 0°, 0°). When every rest angle is a multiple of `q`, `worldAngle = parent.worldAngle + rest.angle + a`.

### Worked example

Shoulder (root) rest `(10, 4)` at 90°, elbow rest `(0, 6)`, wrist rest `(1, 5)`, `q = 1`. Keys: shoulder 30°, elbow 15.3°.

| Bone     | `a` | `rotation` | `restAngle` / `worldAngle` | pivot                                                                                   |
| -------- | --- | ---------- | -------------------------- | --------------------------------------------------------------------------------------- |
| shoulder | 30  | 30         | 90 / 120                   | `(10, 4)`                                                                               |
| elbow    | 15  | 45         | 90 / 135                   | `rotatePoint(0, 6, 30°)`: `C = 56756, S = 32768` → `(−3, 5.196)` → `(−3, 5)` → `(7, 9)` |
| wrist    | 0   | 45         | 90 / 135                   | `rotatePoint(1, 5, 45°)`: `C = S = 46341` → `(−2.828, 4.243)` → `(−3, 4)` → `(4, 13)`   |

With no keys the same rig gives `(10, 4)`, `(10, 10)`, `(11, 15)`: the authored rest pose, at any quantum and any rest angles.

**The fixture, frame 0** (`test/arm-swing.test.ts`; shoulder `(16, 8)`, elbow rest `(2, 9)`, wrist rest `(−1, 8)`; shoulder key −30°, elbow key 50°): the elbow is `(16, 8) + rotatePoint(2, 9, 330°)` = `(16, 8) + round(6.232, 6.794)` = `(22, 15)`; its rotation is 330 + 50 = 20°; the wrist is `(22, 15) + rotatePoint(−1, 8, 20°)` = `(22, 15) + round(−3.676, 7.176)` = `(18, 22)`. Rounding the float chain per bone instead (the jitter bug) gives `round(18.556, 21.970)` = `(19, 22)`: the forearm vector becomes `(−3, 7)` on this frame and `(−4, 7)` on the next, although the forearm does not rotate between them. **Frame 3**: shoulder ease −30 → 30 at `t = 1/2` gives 0°, elbow ease 50 → −10 gives 20°, so the elbow is `(18, 17)` and the wrist `(14, 24)`.

## Rounding: half away from zero

Both quantisation and `rotatePoint` round half away from zero (FR-RIG-12, ADR-010). It is odd-symmetric, so **negating every key angle negates every resolved angle exactly**, and mirroring a rig (rest `x → −x`, angles and offset `x` negated) mirrors every pivot exactly: what "paste mirrored" (FR-RIG-17, T3.6) relies on. Both are property-tested. The price: it does not commute with translation at an exact tie. An interpolated offset of exactly `k + ½` can shift by one pixel more than a translated copy (offsets 0 → 1 give 1 at the midpoint, −1 → 0 give −1). Rest positions and keyed offsets are always translation-exact.

## Validation

`rig` never assumes core's `validate()` ran. `RigError` codes: `DUPLICATE_BONE`, `UNKNOWN_BONE` (a parent, rest entry, bone key or pose entry for a bone the rig lacks), `CYCLE` (I1, self-parent included), `UNKNOWN_FRAME`, `UNKNOWN_VIEW`, `BAD_QUANTUM` (not a valid schema `AngleQuantum`: a multiple of 0.25 in `(0, 90]` dividing 360; the rule is `isValidAngleQuantum` / `angleQuantumSteps` from `@pixel-forge/schema`, the same one the document schema uses), `BAD_VALUE` (a non-finite angle; a rest position or offset that is not an integer of magnitude ≤ 2^31, raster's `MAX_ROTATE_COORD`; an unknown `interp`, also in `interpWeight`, whose position must satisfy `0 ≤ i ≤ n`, `n ≥ 1`; a quantised key angle of 2^51° or more). A `Record` entry whose value is `undefined` (a bone key, or a view's rest entry) is skipped, never an error. Record lookups read own properties only.

## Evidence (tests)

- **(a) Independent reference** (`test/float-reference.ts`, `test/reference.test.ts`): an independent implementation of the whole chain, run on 1000 seeded random forests (up to 9 bones, 16 frames, all quanta, ties seeded on purpose). Offsets, angles with 1/8° operands (every `(k + ½)·q` tie of the tested quanta) and rest sums are computed in exact integer arithmetic; rotations use `Math.cos`/`Math.sin` except where the trig value is exactly known (multiples of 90° and 30°, where float64 `sin 30°` is `0.49999999999999994`). All **42 881** bone evaluations match `evaluatePose` exactly, **exact ties included**: 5 183 key angles, 1 005 offsets, 3 387 rest sums and 22 rotated rest offsets are compared as ties (e.g. `(1, 0)` at 30° is exactly `(0.866, 0.5)` in Q16 → `(1, 1)`). Only genuinely float-ambiguous quantities are not compared exactly: 4 rest sums with a non-1/8 operand and 25 rotated coordinates within the Q16 table error `(|dx| + |dy|) / 131072` of .5 (ADR-010). There the reference accepts either neighbouring rounding, checks that the implementation chose one of them, and continues from that choice, so no bone is skipped and descendants of a tie are compared exactly (in 1 of the 29 float64 would have rounded the other way). The counts are pinned.
- **(b) Translation**: moving a root's rest position by `k`, or adding a constant root offset key `k`, moves every pivot of its tree by exactly `k` (200 random rigs each). The tie exception above is a pinned test too.
- **(c) Per-frame bound**: (rotations and offset keys from the reference, not from the code under test) over 11 188 consecutive frame pairs (loop seams included) of 400 random rigs, the parent → child vector changes by ≤ `ceil(L·Δθ) + 1` per axis; it never needs the `+ 1` (≤ `ceil(L·Δθ)` everywhere), and it is unchanged on all 5 133 pairs where the parent's rotation is unchanged.
- **(d) Hand-written tables** (`test/interp.test.ts`): step, linear and ease, the previous key's interp, hold before and after (once, pingpong), loop wrap (linear and eased), single keys, quanta 5 and 0.25, ties, multi-turn angles, offsets, flipX, independent channels.
- **(e) Arm swing** (`test/arm-swing.test.ts`): 12 frames, shoulder ±30° eased, elbow counter-rotating on the forward swing so the forearm keeps a 20° rotation, then lagging. The 12-frame pivot table is an independently derived golden (from the reference above, "golden reviewed: derived from independent reference, 2026-10-27"; the committed SHA is a secondary pin), and Δθ comes from the reference's own accumulation of the input keys. Every joint stays within `ceil(L·Δθ)` per frame, and the forearm vector is exactly constant over frames 0–6. The deliberately wrong method (each pivot rounded from the float chain) breaks the tight bound on 0→1 and 5→6, where the forearm does not rotate but the wrist jumps 1 px against the elbow. Note: the wrong method **cannot** break `ceil(L·Δθ) + 1`: per axis it moves the vector by less than `|Δv| + 2`, i.e. at most `ceil(|Δv|) + 1`. The test asserts that too, so the tight bound and the rigidity property are the ones that catch the bug.
- **(f) Determinism**: a committed SHA-256 of the fixture's canonical pose table; repeated evaluation is identical; and with `Math.sin/cos/tan/atan/atan2/asin/acos/sinh/cosh/tanh` stubbed to throw, the fixture and 100 random rigs evaluate unchanged.

Coverage: 100 % of lines, 95 % of branches.

## Notes for consumers

- **T3.2 (templates, rest poses, pivots):** author rest positions as canvas offsets at rest (child pivot − parent pivot, both as drawn); no inverse rotation is needed and every pixel is reachable. Rest angles are parent-relative bone directions and do not move pivots. Use `boneOrder` for outliners and anything that walks the tree.
- **T3.3 (part render):** done, see "Part render and overrides (T3.3)" below. Part keys use `keySpan` (hold before the first key, loop wrap).
- **T3.4 (joint check):** done, see "Joint check (T3.4)" below. The sweep is `snapSkeleton(rig, view, new Map([[B, {angle: θ}]]))`. `pivot` = B's rest pivot (B's own rotation never moves it), `childDir` = B's `restAngle` at the quantum used (0.25 gives the finest table direction).
- **T3.6 (pose clipboard):** key angles are relative to rest, so "paste mirrored" negates `angle` (and swaps `_l`/`_r`). Quantisation is odd, so the pasted pose evaluates to exactly the negated rotations. Whether to negate offset `x` is T3.6's call.

## Templates, part names and overlap binding (T3.2)

- `humanoidSide(opts?)`, `humanoidFront(opts?)`, `humanoidBack(opts?)` return a `SkeletonTemplate {name, view: {name, directions}, bones, z}`; `bones` are parents first with exactly the spec names (`root, pelvis, torso, neck, head, upper_arm_l/r, lower_arm_l/r, hand_l/r, thigh_l/r, shin_l/r, foot_l/r`) and a bone's `rest` is `{x, y, angle}`: root = canvas pivot (`opts.origin`: the root sits on the feet row), child = canvas offset from the parent pivot at rest (ADR-012), `angle` = parent-relative bone direction (limbs hang at 90, spine points up at -90 for the pelvis, the side foot points +x). Every pivot is rounded once from the absolute position, so offsets are exact differences and `evaluatePose` with no keys returns the authored pixels at any quantum.
- `opts`: `height` (px, default 48, integer 8..1024), `origin` (default 0,0), `proportions` (partial `HumanoidProportions`, fractions of the height; `DEFAULT_PROPORTIONS`: ankle .04, shin .21, thigh .21, pelvis .06, torso .26, neck .04, head .18 (sum 1); shoulderDrop .03, upperArm .14, lowerArm .12, hand .05, footLength .12; front/back shoulderHalfWidth .12, hipHalfWidth .05). At 48 px: hip 22 px above the feet row, shoulder 36, head top 48. Side: `_r` is the near limb (z above), both limbs on the centre line. Front: `_l` at +x on screen; back mirrors it.
- `parsePartLayerName('part:<bone>[.<part>][@<variant>][#<view>]') -> {bone, part?, variant?, view?} | null`; segments are schema names. **Decision**: document layer names cannot contain `:`, `@`, `#` (I7), so the syntax lives only in source layer names (Aseprite). T4.5 parses the raw name, gives the document layer the plain name `partLayerName(parsed)` = `<bone>`, or `<bone>_<part>` when a `.part` is given (several parts per bone, e.g. arm plus sleeve, each with its own z; `PartName` = layer name; the caller must check the 48-character limit and document-wide uniqueness and refuse, never rename), and turns `@variant` / `#view` into `Variant.name` (default `DEFAULT_VARIANT_NAME` = `default`) / `Variant.viewId` (view looked up by `View.name`; none: the first view). Core's `bindParts` accepts `rawNames` for exactly this.
- `bindByOverlap(parts, {bones: [{id, parentId?, length}], view}, opts?) -> {assignments, ambiguous, unmatched}`. A part is `{layerId, x, y, w, h, alpha?}` (canvas box, `alpha` row-major, > 0 opaque; none: all opaque). A bone's segment is its rest pivot to `pivot + rotatePoint(length, 0, restAngle)`. Each opaque pixel votes for the nearest segment within `reach` (exact BigInt distances; equidistant pixels split the vote); share = votes / all opaque pixels. Thresholds (`DEFAULT_OVERLAP`): `reach` 4 px, `minShare` 0.5, `margin` 0.2 over the runner-up, `candidateShare` 0.15. Assigned only when the best share >= `minShare` and leads by >= `margin`; otherwise `ambiguous` lists the bones with share >= `candidateShare` (best first, ties by id); no pixel within reach (or no candidate) is `unmatched`. Mirrored limbs with identical segments (side view) therefore always come back as candidates.

**Per part, in `rig.parts` order:**

1. **Pose**: `evaluatePose` in `selectView(rig, animation.direction)`; a prepared animation (pose keys, the per-part key index of `variant` / `z` / `visible` and the per-part, per-frame override lists) is cached by animation object. Rotation `none` ignores the angle, so it has one cache entry per variant and flip.
2. **Visibility**: drawn when the bone has a rest entry in the view (`inView`), the `visible` part key (else `view.partVisibility`, else true) is true, and the part has a variant to draw.
3. **Variant**: an explicit `variant` key wins (any variant of the part, even of another view; unknown: `UNKNOWN_VARIANT`). Otherwise, and for `'auto'` until FR-RIG-14 (M1b), the view's default variant: the first with the view's id. A part without a variant in the view is not drawn. **Part keys** (`variant`, `z`, `visible`) step and hold like the bone channels (`keySpan`): before the first key the first key holds, after the last the last one, and a `loop` animation wraps (before the first key the previous loop's last key holds).
4. **Rotation**: residual = `bone.rotation` (no `drawnAngle`, so a part at rest is never resampled) or `worldAngle − drawnAngle`, summed exactly as dyadic rationals and quantised once to the animation's quantum, in `[0, 360)`. `rotateAbout(variant, pivot, residual, part.rotation ?? 'rotsprite')`, then `flipH` about the pivot column when the bone has `flipX`; placed at `offset = snappedPivot − pivotOut`, so the variant's pivot pixel lands exactly on the snapped pivot (sentinel-tested at every 7°). A pivot outside the drawing is honoured by padding the image with transparency first (RotSprite treats the outside as transparent, so the result is unchanged). No new colours (property-tested).
5. **Part overrides**: the frame's overrides with `target: {partId}`, in array order, on the part's own render, both images at `pivot + anchor`: `erase` first (mask value 255 clears; any other value keeps; RGBA masks read alpha, indexed masks the index), then `set` (RGBA: the "over" blend; indexed: every index that is not the `set` image's own `transparentIndex` replaces; an opaque `set` pixel whose index is the part render's `transparentIndex` would erase instead of paint, so it is `BAD_VALUE`, and so is a `set` in the other colour mode). "Empty" means the same everywhere: an index equal to the image's `transparentIndex` (`overrideBox` uses the `set` and `erase` images', `hashRegion` the render's, and the refusal makes them agree on every rendered pixel). A `set` reaching past the part grows the image. Stale overrides are applied like the others (kept, never moved or dropped).

**Cache.** Key: the variant object + its image instance (and `version`, pivot) → `algorithm|angle|flip`. Published document nodes and images are immutable, so the weak keys stay valid across versions and a pivot edit (a new variant object) or a new image misses. Cached images are shared: never mutate a `PartRender` image.

**Staleness (FR-RIG-22).** A part override's `baseHash` covers its region over the part's **pre-override** render, in pivot-relative coordinates (`partTarget`). Translating a part (an offset key, a parent moving it) keeps every pixel around the pivot, so its overrides stay valid; a rotation or a variant switch changes the region and makes them stale; a part that is not drawn makes them `no-target`. The check is content-based: a rotation that leaves the region's pixels identical (a full turn, a region off the art) stays valid. Every override's region is hashed against the render before **all** of the frame's overrides of that target, not after the earlier ones. Final overrides use the same functions with the composite as target (core).

Evidence (`test/render.test.ts`, `test/overrides.test.ts`): W4 as hand-written ASCII (a translated part's override follows it and stays valid, a rotated part's override stays at `pivot + anchor` and goes stale, the untouched part's override stays valid, a variant switch is stale, a hidden part is `no-target`), quarter-turn placements, `flipX`, pivot outside the drawing, `none` / `nearest`, `drawnAngle` residuals at quanta 1, 5 and 0.25, part-key hold and loop wrap, erase-then-set with 255-only masks, indexed overrides, cache hits and misses, cached = uncached, no new colours on 40 random images.

## Joint check (T3.4)

FR-RIG-05, implementing [`docs/contracts/JOINT_CHECK.md`](../../docs/contracts/JOINT_CHECK.md) (T3.0). Read the contract for the exact definition; this is the API.

| Export                     | Purpose                                                                                                                                                                                                                                                                |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jointGaps(input)`         | The pure predicate (contract sections 3.1, 4, 5): `{parent, childRest, frames: [{angle, child}], pivot, childDir, radius}` (RGBA8 images of one canvas, only alpha matters) gives `{pivot, angles: [{angle, gaps}], gapCount, union}`; coordinates sorted by y, then x |
| `jointCheck(input)`        | The rig check (sections 3.2, 6.2): `{view, params, joints: [{bone, parent, pivot, angles, gapCount, union}], summary: {joints, jointsWithGaps, gapCount, unionCount}}`. A rig passes when `summary.gapCount === 0`                                                     |
| `JOINT_RADIUS_DEFAULT`     | 4. The sweep defaults are schema's `JOINT_SWEEP_DEG_DEFAULT` (30) and `JOINT_STEP_DEG_DEFAULT` (5)                                                                                                                                                                     |
| `JointCheckError` (`code`) | `SIZE_MISMATCH`, `BAD_ANGLE` (a frame angle of 0, non-finite or duplicated; a `childDir` that is not a multiple of 0.25), `BAD_RADIUS`, `BAD_PIVOT`                                                                                                                    |

`jointCheck({rig, images, canvas, direction?, partKeys?, palette?, angleQuantum?, rangeDeg?, stepDeg?, radius?, cache?})`: `rig` is a `PartRig` whose bones and views also carry `name` (a schema `Rig` fits), `images` is the `renderParts` lookup, and `canvas` is the document canvas `{w, h}`.

- **Joints**: every bone with a parent bone, when both have a visible part in the view. A bone without visible parts is skipped and its children are not re-attached to a farther ancestor. "Visible" is `renderParts`' rule (rest entry in the view, `visible` key or `partVisibility`), so a visible part that draws nothing still makes a joint.
- **Rendering**: the rest composite is one `renderParts` call. For each joint, B's parts are rendered at each θ = k·S (k ≠ 0, |k·S| ≤ R) with only B's bone key set (relative to rest), one call per angle restricted to B's layers. The pre-override image (`PartRender.base`) is used, so overrides, post-passes, skins and other bones' parts never count. `pivot` is B's snapped rest pivot and `childDir` its `restAngle` at `angleQuantum` (default 1). A private `PartRenderCache` is used unless one is passed.
- **`partKeys`** (variant, `visible`, `z`) apply at rest and at every θ; missing, every part uses the view's default variant. There is no frame: the check is about the rig, not an animation.
- **Indexed variants**: with a `palette` a pixel is opaque when its entry has alpha > 0 (`BAD_VALUE` for an index outside the palette); without one, any index other than the transparent index is opaque.
- **Sweep**: θ are key angles, so an `angleQuantum` coarser than `stepDeg` rounds the rendered rotation (the report still lists θ). `rangeDeg` and `stepDeg` must be > 0 (`RigError('BAD_VALUE')`); a step larger than the range checks no angle; at most 2880 angles. `radius` must be an integer ≥ 1 (`JointCheckError('BAD_RADIUS')`).
- Joints are sorted by bone name in code-unit order and `view` is the view's name.

Evidence (`test/joint.test.ts`): every `fixtures/joint/*.txt` runs through `jointGaps` and deep-equals its hand-written `*.expected.json` (JSON key order and frame-order independence too); the radius, window-edge, off-canvas pivot and error cases the fixtures do not pin; `jointCheck` on a rig built from the fixtures through the real RotSprite (`gappy_elbow` finds (7,6) at −30° and (7,4) at +30°; `clean_capped_elbow` is clean at all 12 angles), plus sweep parameters, skipped bones, view selection and indexed images. The synthetic hero is not clean under the definition: its test (`packages/io/test/hero-fixture.test.ts`) pins the 8 gap pixels.

## Edit attribution (T3.8)

FR-RIG-22 ("drawing on a rig frame writes a part override if the stroke falls within one part's area, otherwise a final override") and FR-RIG-24 (`pf override import`). `attribute.ts`; core's `attributeEditTx` builds the context from `renderStages` and writes the result.

| Export                                                          | Purpose                                                                                                                                                                                                                 |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `attributeEdit(ctx, before, edited)`                            | `AttributedOverride[]`: the overrides that make the frame render as `edited` (RGBA, the size of `before`). Part overrides in `ctx.parts` order, then at most one final override; `[]` when nothing visibly changed      |
| `EditContext {parts, finalOnly?, render, palette?, colorMode?}` | The frame as the attribution sees it (the card's `renderCtx`): the drawn parts (`renderParts` output) and `render(parts) -> EditRender {finalTarget, result}`, the frame re-rendered with changed part images           |
| `AttributedOverride {target, anchor, set?, erase?, baseHash}`   | A schema `Override` without ids: images inline (`set` in the target's colour mode, `erase` an 8-bit `IndexedImage` mask, 255 where it clears). The caller creates the images and ids and appends the overrides in order |

**The context.** `parts` are the parts this render draws, after their existing part overrides (`image`, `offset`), with `base` and `pivot` for the anchor and the hash; a part's **footprint** is the canvas pixels where its `image` is not transparent (an indexed image: neither its transparent index nor any palette entry of alpha 0, spec 3.4 clarification 8). `render(parts)` re-renders the frame with those part images (composite, post-passes, existing final overrides; no skin) and returns `result` (the finished frame; `render(ctx.parts).result` is what `before` must be) and `finalTarget` (the canvas before every final override, the target of a final override's `baseHash`). Core: `renderStages(...).result` and `.beforeFinals` (`.beforeMirrorFinals` for a mirror) of the export render, the same render `checkOverrides` hashes finals over (T3.3 doubt 2). `finalOnly: true` gives only final overrides (a mirror: its part overrides are T3.6's) while `parts` stays the real list that `render` draws. `before` must be `render(ctx.parts).result` (by pixel hash, alpha-0 pixels equal): otherwise `RigError` `BAD_ARGUMENT` with `reason: 'before-mismatch'` (checked once something changed; the render is reused when no part candidate exists).

**Rules.**

1. Changed pixels: where `before` and `edited` differ, every alpha-0 pixel counting as the same transparent. They are split into **8-connected components** (scan order).
   **Attribution rule: each 8-connected stroke becomes a part override if it lies inside exactly one part's footprint, otherwise it goes into the single final override.**

2. A component (stroke) is a **part candidate** when every one of its pixels lies in the footprint of exactly one part, the same part for all; a pixel outside every part, or under two overlapping parts, sends the whole component to the final override. So a stroke that crosses from one part into another (or off the silhouette) is final; separate strokes on two parts are two part overrides.
3. **Part overrides** (one per part; its components merged) are painted on the part's current image: alpha-0 edit → erase (an 8-bit `IndexedImage` mask, value 255, in every colour mode); opaque edit → set; translucent edit → erase then set (it replaces, it does not blend). Indexed parts take the lowest palette index of exactly the edited colour (else the component is demoted). The frame is re-rendered with the new part images; a component whose pixels do not come out exactly as `edited` (a layer above, layer opacity, an existing final override over it, a post-pass) is **demoted** to the final override, and the render repeats until every candidate left reproduces its pixels. Anchor: the bbox top-left minus the part's snapped pivot. `baseHash` over `partTarget(part)`, so it follows a translation and goes stale on a rotation or a variant switch.
4. **The final override** covers every pixel where that last render still differs from `edited` (the final and demoted components, and anything a post-pass moved), painted over the finished frame with the same erase / set rule: `composite` copies an opaque colour, or any colour onto a transparent pixel, exactly, so the result is exact. Anchor: the bbox top-left in canvas pixels. `baseHash` over `finalTarget` of that render (with the new part overrides in place). `colorMode: 'indexed'`: the `set` image is indexed, its transparent index the palette's first alpha-0 entry; a colour the palette lacks is `BAD_VALUE`.
5. Each `baseHash` is computed by calling `baseHash` itself (the function `checkOverride` uses) on the images about to be stored, so a freshly attributed override is never stale.

**Round trip.** Rendering the frame with the overrides appended gives `edited` exactly (alpha-0 pixels as `(0,0,0,0)`), and every new override checks valid. A new part override does change the canvas under the frame's **existing** final overrides: one whose region (bbox ±1) it touches goes stale, and is still applied; so can the mirrors' finals when the import is into their source (KNOWN_ISSUES RIG-04; core's `attributeEditTxReport` lists them).

Evidence (`test/attribute.test.ts`, hand-written ASCII): an edit inside one part (part override, anchor and `set` image), an edit straddling two touching parts (final), an erase at the silhouette (part erase mask, two components merged), an addition just outside a silhouette (final) next to separate leg and arm edits (two part overrides), edit then re-pose (follows a translation, stale on a 90° rotation), translucent edits, a part pixel under a layer above (demoted), overlapping parts (final), edits on top of earlier overrides, indexed parts and indexed finals; every case asserts the pixel-hash round trip and that the new overrides are valid.
